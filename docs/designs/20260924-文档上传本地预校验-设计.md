# 文档上传本地预校验 设计

- 关联需求：SPEC.md#11-上传前本地预校验、spec/20260924-文档上传本地预校验/需求与技术对照.md
- 作者 / 日期：Codex / 2026-09-24

## 现状

上传入口只有一个：知识库页面的手动上传（`:auto-upload="false"`）。

| 层 | 现在的行为 | 位置 |
| --- | --- | --- |
| 前端 | 选中文件只做一件事：`selectedFile.value = uploadFile.raw`，不看大小、不看是否为空；`accept=".pdf,.doc,.docx,.txt"` 只过滤扩展名 | `smrag-web/src/views/Knowledge.vue` |
| 后端（multipart 层） | `spring.servlet.multipart.max-file-size: 20MB`，超限时在解析阶段直接中断请求 | `smrag-core/src/main/resources/application.yml` |
| 后端（业务层） | `validateFile` 依次校验：空文件 → 文件名空 → `size > maxUploadSizeBytes`；超限抛 `IllegalArgumentException("文件大小超过允许上限")` | `smrag-core/src/main/java/com/hqc/smrag/service/knowledge/DocumentService.java:452` |
| 上限口径 | `RagProperties#maxUploadSizeBytes`，默认 `20L * 1024 * 1024`，与 `application.yml` 的 `smrag.rag.max-upload-size-bytes: 20971520` 一致 | `smrag-core/src/main/java/com/hqc/smrag/config/RagProperties.java:143` |

问题在于**反馈点太靠后**：用户选中一个远超上限的文件，会先等文件传输（或等 multipart 中断），才拿到一次失败。
体验上的失败方式还不统一：走业务层是中文提示，走 multipart 层是容器抛出的异常。

## 目标与约束

- 目标：把失败点提前到「选中文件」，且提示可读；前端口径与后端一致。
- 约束：
  - **不改后端**：不调整上限、不改拒绝行为、不新增接口；后端仍必须能挡住绕过前端的请求（前端校验是体验优化，不是安全边界）。
  - **不引新依赖**：纯函数实现，不新增第三方库。
  - **按项目现状写 JavaScript**：`smrag-web` 无 `tsconfig`、无 `lang="ts"`，本次不引入 TypeScript（与 `docs/14-前端规范-Vue3.md` 的 TS 要求存在差异，已登记为需求待确认项 2）。
  - 提示文案复用现有 `copy` 文案对象，不散落在模板里。

## 方案

**选定：抽出纯函数 + 常量独立成文件。**

```text
constants/uploadLimits.js   →  MAX_UPLOAD_SIZE_BYTES = 20971520
utils/uploadGuard.js        →  validateUploadFile(file) → { ok, code, message }
views/Knowledge.vue         →  handleFileChange 校验一次；handleUpload 发送前再校验一次
```

`validateUploadFile` 的判定顺序与后端 `validateFile` 对齐（先空、后超限），保证两端对同一个文件给出同一个结论：

| 输入 | `code` | `message` |
| --- | --- | --- |
| `null` / `undefined` / 非对象 | `MISSING` | 请先选择要上传的文件 |
| `size <= 0` | `EMPTY` | 文件内容为空，无法解析 |
| `size > MAX_UPLOAD_SIZE_BYTES` | `TOO_LARGE` | 文件超过 20MB 上限，请压缩或拆分后重试 |
| 其余 | `null`（`ok: true`） | — |

提示里的「20MB」由常量换算而来，不写死两处，避免改了常量却漏改文案。

**为什么不用 Element Plus 的 `before-upload`**：当前上传是手动模式（`:auto-upload="false"`），`before-upload` 不会触发；要用它就得改成自动上传，等于顺带改掉现有交互，超出本需求范围。

**为什么不用 `@vueuse/core`**：项目里已经有这个依赖，但这里只需要一次数值比较，引入 composable 反而增加耦合面。

**为什么必须抽成独立模块**：项目的测试基座是 `node --test`（见 `smrag-web/package.json` 的 `test` 脚本），只能直接运行纯 ESM 模块。判断逻辑写在 `.vue` 的 `<script setup>` 里就无法被自动化测试覆盖，「新增或修改的逻辑有对应测试」这条门禁会直接失效。

## 风险评估

| 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- |
| 前端常量与后端 `max-upload-size-bytes` 漂移，出现「前端放行、后端拒绝」 | 中 | 中 | 常量集中一处并注释指向后端；SPEC.md 记口径；后续可考虑由接口下发上限（已列入范围外） |
| 前端校验被误当成安全边界，后端校验被削弱 | 低 | 高 | 设计明确「前端只是体验优化」；本次不改后端任何代码 |
| 校验在两处各写一份 `if`，日后只改一处 | 中 | 中 | 两处调用同一函数，模板与提交逻辑里都不出现裸比较 |
| 提示文案与项目既有提示风格不一致 | 低 | 低 | 复用 `copy` 文案对象与 `ElMessage`，与 `notifyError` 同级 |
| 影响既有上传相关测试 | 低 | 高 | 改动前已记录测试基线（66 个用例 / 65 通过 / 1 失败），改动后逐项对比 |

## 回滚方式

无接口、无数据、无配置变更，回滚只涉及代码。

整体回滚（推荐）：

```bash
git revert --no-edit <本需求在主干上的合并提交>
```

分支上人工回滚（尚未合并时）：

```bash
git switch feat/upload-size-guard
git checkout master -- smrag-web/src/views/Knowledge.vue
git rm smrag-web/src/constants/uploadLimits.js smrag-web/src/utils/uploadGuard.js smrag-web/tests/uploadGuard.test.js
git commit -m "revert(upload): 移除上传本地预校验"
```

验证回滚是否干净：

```bash
cd smrag-web && npm test     # 应回到基线：66 个用例 / 65 通过 / 1 失败
git status --porcelain       # 应只剩与本需求无关的未跟踪文件
```
