### 与后端口径对照（R2-2）

| 判定顺序 | 后端 `DocumentService#validateFile:452` | 前端 `utils/uploadGuard.js` | 是否一致 |
| --- | --- | --- | --- |
| 1 | 文件为空 → `文件不能为空` | 非对象 → `请先选择要上传的文件` | 一致（前端把「没选文件」也在这一步挡住） |
| 2 | `file.isEmpty()`（0 字节）→ `文件不能为空` | `size <= 0` → `文件内容为空，无法解析` | 一致（同一条规则，前端文案更具体） |
| 3 | 文件名为空 → `文件名不能为空` | 文件名为空字符串 → `文件名为空，无法上传` | 一致 |
| 4 | `size > maxUploadSizeBytes` → `文件大小超过允许上限` | `size > MAX_UPLOAD_SIZE_BYTES` → `文件超过 20MB 上限，请压缩或拆分后重试` | 一致（阈值相同，前端补出具体上限值） |

判定顺序相同意味着：同一个文件在两端会落在同一个分支，不会出现「前端说 A、后端说 B」。

## 未覆盖项（明确说明）

1. **界面实际表现未做端到端点击验证。** `知识库` 页面需要登录态、后端服务与数据库才能打开，
   本次只验证到「判定逻辑 + 页面接线」两层（接线由 `wires the guard into the knowledge upload view` 用例断言），
   没有在真实浏览器里点选 200MB 文件观察 toast 文案。合并前建议在联调环境人工过一遍：
   选超限文件 → 应看到提示且网络面板无请求；选 0 字节文件 → 应看到提示且无请求。
2. **「选中非法文件后清空已选」的交互未由需求方确认。** 本次按设计选中即清空，
   另一种做法是保留选择、只置灰上传按钮（计划文档检查点已列出，待产品确认）。
3. **后端拒绝路径未回归。** 前端改动不影响后端，但本需求没有跑后端测试（改动未触及 Java 代码，
   `mvn test` 的基线未记录）。若要与后端一起回归，需要单独一次带 JDK 17 的环境执行。
4. **multipart 层的中断行为未验证。** 超过 `spring.servlet.multipart.max-file-size` 时容器层如何响应，
   后端仍可能抛出非中文异常；本次只覆盖了业务层可达的路径。
