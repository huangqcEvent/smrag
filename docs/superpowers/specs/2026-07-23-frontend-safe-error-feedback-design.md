# 前端安全错误反馈设计

## 目标

前端只展示用户可以理解和采取行动的错误提示。任何请求路径都不得直接展示 Axios、HTTP、SQL、Java 堆栈等技术信息，也不得展示后端兜底文案“系统繁忙，请稍后重试”。同一次失败最多产生一次错误弹窗。

## 错误分类

错误提示按以下优先级生成：

1. 用户主动取消或中止请求：不弹窗。
2. 登录失效：提示“登录已过期，请重新登录”，并保持现有退出和跳转逻辑。
3. 400、403、404、409 等明确业务错误：保留后端返回的安全业务文案。
4. 请求超时：提示“请求超时，请检查网络连接”。
5. 无响应或网络错误：提示“网络连接异常，请检查网络”。
6. 500 及其他服务端未知异常：提示调用方提供的操作级文案；没有操作级文案时使用“当前操作未完成”。
7. 其他未知异常：使用同样的操作级兜底规则。

以下内容始终被视为不安全文案，不能直接展示：

- `系统繁忙，请稍后重试`
- `Request failed with status code ...`
- `Network Error`
- Axios 超时原文
- SQL、Java 异常类名、堆栈和包含内部实现细节的文本

## 架构

新增一个独立的错误反馈模块，负责：

- 从 Axios、Fetch/SSE 和普通 `Error` 中提取状态与业务消息。
- 过滤技术文案并生成安全的用户提示。
- 通过同一个通知函数展示错误。
- 记录已经通知过的错误对象，避免响应拦截器和页面 `catch` 重复弹窗。

Axios 响应拦截器继续承担全局通知职责，但必须先通过安全错误模块规范化。页面和流式聊天不再直接读取 `error.message`，统一调用同一通知函数并传入操作级兜底文案。

SSE 事件中的错误消息在写入聊天消息状态和弹窗前也必须经过相同的安全化函数，避免技术信息以内联错误的形式泄漏。

## 交互与文案原则

- 一个失败只出现一个错误弹窗。
- 优先说明失败的操作，例如“新增角色失败”“文档加载失败”。
- 不向用户展示 HTTP 状态码、库名称或异常类名。
- 不使用“系统繁忙”解释未知故障。
- 用户取消确认框、主动停止回答等正常行为不属于错误。

## 测试

纯函数测试覆盖业务文案保留、500 文案替换、Axios 原始错误过滤、超时、断网和操作级兜底。通知测试覆盖同一错误对象只弹一次以及取消请求不弹窗。现有前端全量测试和生产构建必须继续通过。
